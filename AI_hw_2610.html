SEA 市場數據分析BigQuery 知識庫的建立與應用

將常用資料表、指標定義與適用情境整理成專案知識，減少每次提問時重複說明背景的負擔。

本次介紹知識庫的組織方式、文件內容與 AI 協作過程，並透過分析案例說明實際應用。

知識庫文件由 AI 協助建立初稿，再由我做確認與調整。

AI 參照知識庫文件內容，協助查詢數據、解讀資料與呈現分析結果。

01 · 建立目的

把查詢所需的背景知識留在專案中

日常分析的問題可能很簡短，但要讓 AI 正確理解，往往需要先交代市場、資料表與計算口徑等背景知識。

提問前需要交代的資訊

  • 資料屬於哪個市場？依市場區分專案與知識庫，明確指定查詢環境。
  • 該使用哪張資料表？說明常用資料表的用途、查詢優先順序與適用情境。
  • 該取哪些欄位、如何計算？確認欄位定義、篩選條件、指標公式與關聯方式。

既有知識的來源

  • BigQuery 資料表資訊欄位定義與說明，以及資料表的分區設定。
  • 數據職能經驗選表優先順序、查詢條件、欄位記錄邏輯與常用觀察指標。
使用目標

將這些知識整理成可持續參考的文件，讓後續提問聚焦於「想了解什麼」，減少重複說明查詢背景的負擔。

資料表說明 記錄一般遊戲歷史押注分析用途、不含當日的資料範圍、分區欄位與來源中繼表。 是否適合目前問題與日期範圍。

查詢與指標計算規則 記錄日期篩選、ItemUse = 0、平台總押量、押注段與 RTP 公式，以及客群門檻與計算方式。 如何得到符合業務口徑的數值與分群。
關聯定義表 列出遊戲、遊戲類別、橋段與廳館的定義表，以及完整關聯條件。 如何將代碼對應到正確的分類與名稱。

實例一：押注量與押注段的單位不同

一般押注表的現行文件

RatioTotalBet 的單位是金幣，分群押量使用 SUM(RatioTotalBet)。

BetValue 的單位是分數。文件對魚機、棋牌、撲克的押注段定義為 BetValue / 1000；老虎機則為 (BetValue * BetLines) / 1000。

將單位與公式分別寫清楚，避免把押注段換算套用到已是金幣的總押注欄位。

實例二：一般遊戲押量與平台總押量的範圍

一般押注表與平台遊戲表的現行文件

一般押注分析預設使用一般遊戲表。計算平台總押量時，還須加入平台遊戲資料。

文件明列兩張表名，要求依共同維度各自彙總，再以 UNION ALL 合併加總。

明確區分一般遊戲與全平台的資料範圍，避免漏計平台遊戲押量，或因直接關聯不同粒度的資料而重複計算。

實例三：客群定義包含門檻與計算範圍

一般押注表的客群定義與計算規則

現行文件將客群門檻與計算規則分開，明確記錄各客群的互斥區間。

客群依玩家全平台單日押量判定，每日重新分類，不受分析中的遊戲篩選影響。平台遊戲文件以連結指向完整定義。

將分類門檻與計算範圍一起寫清楚，避免區間重疊，或只用特定遊戲的押量判定客群。

## 2．助理

本專案的操作守則重點如下：

**專案目的**  
用於東南亞（SEA）市場資料查詢。

**BigQuery 操作規則**  
所有 BigQuery 查詢都必須直接透過 MCP 伺服器 `bigquery_sea` 完成：

- SQL 查詢使用 `bigquery_sea.execute_sql`
- metadata 查詢使用：
  - `bigquery_sea.get_table_info`
  - `bigquery_sea.list_table_ids`
  - `bigquery_sea.search_catalog`
- 不使用 `bigquery_sea.ask_data_insights`
- 不使用本機 `bq` CLI、`gcloud`、Python SDK、外部 API 或其他非 MCP 路徑
- 不要求使用者執行 `gcloud auth login`
- 不要求啟用 `Data Analytics API with Gemini`

**BigQuery 環境**  
- 專案：`tapirus`
- 主要資料集：`Custom_Tapirus`
- 備份資料集：`Custom_Tapirus_Backup`，查詢時不使用

**資料表使用規則**  
- `TableName`：即時資料表，只保留最近 7 日含當日資料；僅查詢當日資料時使用
- `_p_TableName`：中繼資料表，保留所有歷史資料但不含當日；日常查詢優先使用
- `Tableau_TableName`：彙整表，用於降低 BigQuery 查詢費用；若有特別註明，優先於中繼資料表使用
- `DimTableName`：定義表，用於查詢欄位值與代號定義
- `SpecialUser`：社交玩家／幣商資料表

**查詢注意事項**  
- 除定義表與 `SpecialUser` 外，其餘資料表皆為分區資料表
- 分區欄位是 `ProDate`，型別為 `DATE`
- 查詢分區資料表時一定要加上 `ProDate` 條件
- 執行查詢前，若預估處理資料量超過 3 GB，必須先提示並取得同意後才能執行查詢。

## 4．助理

可以，而且建議把「操作守則」和「資料表知識」分開管理。

Codex 專屬、會被我優先遵守的是 **`AGENTS.md`**。它適合放「我在這個專案中應該怎麼做」的規則，例如 BigQuery 一律走 `bigquery_sea`、查分區表一定要加 `ProDate`、不可用 `bq CLI` 等。

但「常用資料表用途與欄位說明」比較像知識文件，不建議全部塞進 `AGENTS.md`，否則會越來越長、難維護。比較正確的做法是：

```text
SEA/
  AGENTS.md
  docs/
    data-tables/
      README.md
      common-tables.md
      User.md
      _p_User.md
      Tableau_RevenueDaily.md
      DimGame.md
      SpecialUser.md
```

**建議分工**

`AGENTS.md` 放 Codex 操作規則與文件索引，例如：

```md
## 常用資料表文件

常用資料表用途與欄位說明維護於 `docs/data-tables/`。

查詢前若涉及常用資料表，應優先參考：
- `docs/data-tables/README.md`
- 對應資料表說明文件
```

`docs/data-tables/README.md` 放總覽，例如：

```md
# 常用資料表總覽

| 資料表 | 類型 | 用途 | 查詢優先順序 |
|---|---|---|---|
| `_p_User` | 中繼表 | 玩家基本資料歷史 | 日常查詢優先 |
| `User` | 即時表 | 今日玩家資料 | 僅查詢當日 |
| `SpecialUser` | 定義/特殊表 | 社交玩家、幣商名單 | 可直接查 |
```

```md

- 查玩家註冊來源

- 若查詢範圍過大，需先估算資料量
```

## 6．助理

`docs/` 是「專案文件總資料夾」，`docs/data-tables/` 是其中一個分類。這樣做的原因是避免未來文件全部堆在 `docs/` 根目錄，表一多就會變得很難找。

你可以把它想成：

```text
docs/
  data-tables/      # 資料表用途、欄位、查詢注意事項
  queries/          # 常用 SQL 範例或查詢模板
  metrics/          # 指標定義，例如 DAU、ARPU、留存
  dimensions/       # 維度代碼說明，例如平台、國家、遊戲類型
  workflows/        # 固定分析流程，例如營收分析、活動成效分析
```

不一定一開始都要建立。若目前只想整理資料表，那只需要：

```text
docs/
  data-tables/
    README.md
    _p_Player.md
    SpecialUser.md
```

我會建議先用 `docs/data-tables/`，因為你的需求是「常用資料表的用途與欄位說明」，它本身就是一個穩定分類。未來如果你開始整理「常用查詢 SQL」、「業務指標定義」、「分析流程」，再放到 `docs/queries/`、`docs/metrics/`、`docs/workflows/` 這類資料夾就好。

### 助理

是，理解正確。這句話的意思是：

1. 兩張表套用相同日期與相容的查詢維度。
2. 各自計算 `SUM(RatioTotalBet)`。
3. 使用 `UNION ALL` 合併兩張表的彙總結果。
4. 最外層再次加總，得到平台總押量。

不建議直接 `JOIN`，因為兩張表的資料粒度與維度不同。若關聯鍵無法唯一對應，容易形成多對多關聯，使資料列展開，造成兩邊的 `RatioTotalBet` 被重複計算。

概念上應採用：

```sql
WITH BetData AS (
  SELECT
    ProDate,
    SUM(RatioTotalBet) AS RatioTotalBet
  FROM `SEA_PROJECT.DATASET.Tableau_BetWinLogByHour`
  WHERE ProDate BETWEEN @StartDate AND @EndDate
  GROUP BY ProDate
),
PlatformGameData AS (
  SELECT
    ProDate,
    SUM(RatioTotalBet) AS RatioTotalBet
  FROM `SEA_PROJECT.DATASET.Tableau_PlatformGameDetailBetWinLog`
  WHERE ProDate BETWEEN @StartDate AND @EndDate
  GROUP BY ProDate
)

SELECT
  ProDate,
  SUM(RatioTotalBet) AS PlatformTotalBet
FROM (
  SELECT * FROM BetData
  UNION ALL
  SELECT * FROM PlatformGameData
)
GROUP BY ProDate
```

使用 `UNION ALL`，而不是 `UNION`，避免剛好相同的彙總值被去重。

若要讓文件更直接，原句可改成：

> 平台總押量計算方式：兩張表套用相同日期條件，分別依共同查詢維度彙總 `RatioTotalBet`，再以 `UNION ALL` 合併結果並加總；不得直接 `JOIN` 不同資料粒度的資料，以免產生多對多關聯而造成押量重複計算。

## 查詢與指標計算規則

- 日期篩選條件一律使用 `ProDate`，不使用 `CreateDate`。
- 預設加入 `ItemUse = 0`，排除使用道具的資料；只有查詢需求明確要求包含道具使用時，才能取消此條件。
- 平台總押量計算方式：本表與 `Tableau_PlatformGameDetailBetWinLog` 套用相同日期條件，分別依共同查詢維度彙總 `RatioTotalBet`，再以 `UNION ALL` 合併結果並加總；不得直接 `JOIN` 不同資料粒度的資料，以免產生多對多關聯而造成押量重複計算。
- 押注段計算方式：
  - 魚機、棋牌、撲克遊戲： `BetValue / 1000`
  - 老虎機： `(BetValue * BetLines) / 1000`
- RTP 計算方式：
  - 老虎機：`SAFE_DIVIDE(SUM(RatioTotalWin) + SUM(JackpotWin), SUM(RatioTotalBet))`
  - 其他遊戲類別：`SAFE_DIVIDE(SUM(RatioTotalWin), SUM(RatioTotalBet))`
- BuyBonusID 尾數對應押注段倍數：
  - 1：50倍
  - 2：100倍
  - 3：150倍
  - 4：200倍
  - 5：250倍

### 客群定義

| 客群 | 玩家單日總押注量（單位：金幣） |
|---|---:|
| 超大客 | `15,000,000`（含）以上 |
| 大客 | `5,000,000`（含）～`15,000,000`（不含） |
| 中客 | `1,500,000`（含）～`5,000,000`（不含） |
| 小客 | `150,000`（含）～`1,500,000`（不含） |
| 小小客 | `2,000`（含）～`150,000`（不含） |
| 無效帳號 | 未達 `2,000` |

### 客群計算規則
- 本表與 `Tableau_PlatformGameDetailBetWinLog` 分別依 `ProDate`、`UserID` 加總 `RatioTotalBet`，再以 `UNION ALL` 合併並加總為玩家全平台單日總押注量。
- `Tableau_BetWinLogByHour` 預設套用 `ItemUse = 0`；`Tableau_PlatformGameDetailBetWinLog` 無此欄位，不套用該條件。
- 客群一律依玩家全平台單日總押注量判定，不受遊戲、廳館等分析維度篩選影響。
- 客群按日重新計算，同一玩家在不同日期可能屬於不同客群。
